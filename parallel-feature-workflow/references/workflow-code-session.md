# `workflow-code-session` 编码接入

此模式只在调用方明确指定 `workflow-code-session` 时使用。它是外层 workflow 的 code 阶段接入规则，不替代原独立完整流程；不读取其状态机、manifest、模板或校验器，不输出 `MERGE_READY`，也不自行启动 Review 或修复循环。

## 进入条件与输入

code 主 Agent 在派发前先读取 [agent-dispatch.md](agent-dispatch.md) 的“派发前展示”和“`workflow-code-session` 配置与职责”，按其中的优先级展示有效模型/推理强度、来源和能力核验结果。随后核验以下输入均已明确：

- 任务标识与执行轮次。
- plan 版本与正文入口，以及批准依据。
- 唯一工作目录与允许修改范围。
- commit 计划、验证要求和模型配置。
- 禁止动作，包括未获授权的远端操作、Git 操作和计划外修改。

还须实际核验 plan 的质量结果、适用的独立 Plan Review 结论和批准前提，而非仅接受“已通过”标签。源码修改授权、必要的只读 Git 授权、按计划本地暂存与中文 commit 授权必须分别覆盖本轮任务和允许路径；批准 plan 本身不自动构成 Git 授权。

plan、授权、目录状态或实现前提存在冲突时，停止受影响步骤并把证据、影响的 `AC/STEP/TEST` 和最小修订建议回报主控；Coder 不补造决策或改写方案。多 session 模式由 code 主 Agent 调用本模式；简略模式由当前主 Agent 调用，当前主 Agent 同时承担外层主控和编码协调职责，不创建虚拟 phase session。

## 单工作目录协调

只使用一个工作目录，每个文件有唯一写入负责人。独立且无共享路径的任务可以并行；共享文件或有依赖的任务串行。下游只有在上游完成、验证约定结果并明确释放依赖后才能开始，不能只因上游已启动而解除依赖。

Coder 只在分配路径内编码并回报。只有 code 主 Agent 操作 Git；子 Agent 不暂存、提交、切换分支或修改远端。提交窗口和最终验证窗口前，code 主 Agent 必须确认所有 Coder 停写；此时只暂存本次计划内、可归属的精确修改，并按 commit 计划串行提交。若多个 commit 需要同一文件且无法可靠分离，按 commit 顺序编码和提交，不能先混合修改再猜测拆分。

任务开始时发现既有未提交改动、其他任务写者或无法核实的目录状态，保留现场并回报主控；不得自动 stash、reset、覆盖、删除或清理。提交失败、提交不完整或最终验证失败时同样保留现场并回报，不能交付为可审查完成状态。

## 固定交接与后续处理

全部计划内 commit 和最终验证完成后，code 主 Agent 固定已提交 HEAD，记录完整 commit ID、顺序、目录、基线与工作区状态，并把 workflow 共同的五项结果摘要交给主控：

1. 做了什么。
2. 结论。
3. 产物位置。
4. 未决项。
5. 建议下一步。

摘要另附目录、基线与固定的已提交 HEAD、commit 清单和顺序、验证命令与真实结果、plan 偏差，以及工作区状态和所有 Coder 是否已停止写入。

不得声称已通过尚未执行的 Review。多 session 模式中，code 主 Agent 只维护内部编码任务，不自行安排 Review 或修复；简略模式中当前主 Agent 完成编码协调后，按外层 workflow 的用户选择进入 Review 或修复阶段。

修复只接受主控的新指令：非自动模式必须包含用户选择的修复项，自动模式必须包含符合既定规则的修复项。修复在新一轮中完成并产生新的本地提交后，重新固定 HEAD 并交回主控；旧交接不得被当成新版本的验证或 Review 依据。
