# 方案质量门禁

仅用于完整方案制定或审查。筛查 A-J 的全部检查项并逐项记录，不能删除检查项或仅回答“已考虑”。轻量方案不读取或执行本门禁，也不能声称已通过完整门禁。

只对 `contract_status=就绪` 且由 `quality_subject` 标识的确切方案版本执行最终判定。任务契约待澄清时写 `quality_status=未评估`，不进入本门禁；审查者提出但尚未写入被审版本的建议不能关闭该版本的门禁缺口。

## 导航

- 判定协议
- A-F：需求、证据、架构、正确性、兼容和非功能
- G-J：实施、验证、发布和决策
- 最终判定

## 判定协议

### 逐项状态

- `已满足`：现状判断有可核查证据，未来行为有可执行措施及验证方式。
- `待处理`：仅剩非关键缺口，且已明确责任方或决策来源、处理时点和关闭条件。
- `阻塞`：存在未解决的关键缺口、冲突、依赖或决策，当前不能形成可实施的确定方案。
- `不适用`：检查项确实不涉及本次范围，并给出已检查的边界和依据。

`待确认`不是独立状态，也不等于已满足。需要用户、业务方或外部系统确认时，关键项记为`阻塞（待确认）`，非关键项记为`待处理（待确认）`。

### 关键性

满足任一条件即为关键：

- 可能实质改变范围、架构、公共契约、数据模型、安全权限、兼容迁移、核心验收、发布或回滚。
- 可能导致主路径错误、数据损坏、安全暴露或无法证明需求达成。
- 缺少有权限的决策来源对形成确定设计所必需的上游方向确认。

只有影响边界明确、不会使方案失效、可以安全延期且已有关闭计划的事项，才能判为非关键。无法判断关键性时按关键处理。

### 依据类型

- `事实证据`：代码、配置、文档、测试、运行结果或可定位的外部资料。
- `确认记录`：用户或有权限的决策来源明确确认的内容及版本。
- `推断依据`：从事实证据推导的判断，必须标明不确定性；不能单独关闭关键项。
- `设计措施`：未来要实施的具体动作，必须关联实施步骤、可观察完成标准和验证方式。

现状、调用链、依赖和既有行为必须使用事实证据或确认记录，不能用“实施时再调查”或未来设计措施代替。`不适用`也必须给出范围边界依据。

## A. 需求门禁

- `A1`：目标、范围、不做什么和验收标准是否明确？
- `A2`：用户可见行为和保持不变项是否明确？
- `A3`：是否识别冲突需求、歧义和隐含前提？
- `A4`：方案是否逐项覆盖需求，而非只覆盖主要路径？

## B. 证据门禁

- `B1`：是否读取适用的项目指令、代码、配置、文档和测试？
- `B2`：关键现状判断是否能指向事实证据？
- `B3`：是否区分事实、推断、假设和未知项？
- `B4`：是否避免虚构文件、接口、运行结果或依赖行为？

## C. 架构与影响门禁

- `C1`：是否追踪入口、调用方、被调用方、数据流和状态变化？
- `C2`：是否覆盖公共 API、类型、协议、事件和数据消费者？
- `C3`：是否覆盖数据库、缓存、队列、任务和第三方依赖？
- `C4`：是否说明代码、配置、依赖、文档、构建和运维影响？
- `C5`：是否优先复用现有模式并控制改动范围？

## D. 正确性与边界门禁

- `D1`：是否覆盖正常、异常、空值、极值、重复、乱序和部分失败？
- `D2`：是否覆盖并发、幂等、重试、超时、事务和一致性？
- `D3`：是否定义错误传播、降级和恢复行为？
- `D4`：是否考虑状态迁移和中间态？

## E. 兼容与迁移门禁

- `E1`：是否识别向后兼容、版本差异和隐含调用方？
- `E2`：是否处理存量数据、迁移顺序和新旧版本共存？
- `E3`：是否需要特性开关、灰度、双读、双写或回填？
- `E4`：是否明确不可逆步骤及保护措施？

## F. 非功能门禁

- `F1`：是否覆盖权限、认证、授权、数据暴露和输入安全？
- `F2`：是否覆盖性能、容量、资源上限和热点路径？
- `F3`：是否覆盖可用性、容错、故障隔离、备份恢复及适用的 RTO/RPO？
- `F4`：是否覆盖日志、指标、追踪、审计、告警和运维责任？
- `F5`：是否覆盖不同环境、配置和网络边界？
- `F6`：涉及数据时，是否覆盖隐私、分类、保留删除、脱敏、地域和合规约束？
- `F7`：是否覆盖维护责任、依赖生命周期、许可证和构建或供应链风险？
- `F8`：面向用户时，是否覆盖适用的可访问性、本地化和多终端一致性？

## G. 可实施性门禁

- `G1`：步骤是否写明修改目的、行为前后变化，并定位到文件路径及函数、类、测试、配置键或文档章节等结构位置，且明确标记新增项？
- `G2`：步骤顺序、依赖和前置条件是否明确；跨 Agent 依赖是否包含提供方、产物、契约版本和解除阻塞条件，且 Task Contract 能追溯到对应步骤？
- `G3`：每一步是否有交付物和可观察的完成标准？
- `G4`：是否避免夹带无关重构或超出授权的动作？
- `G5`：涉及长任务时，是否指定唯一状态来源、原始要求留存、里程碑检查点、恢复入口和具体下一动作？
- `G6`：需要派发 Agent 时，是否展示职责、模型/强度、配置来源和可修改提醒，遵循默认继承、用户覆盖优先及后端能力核验，且不追溯修改运行中配置？单 Agent 无派发时可不适用。

## H. 验证门禁

- `H1`：是否为核心行为、失败路径和边界情况设计测试？
- `H2`：是否覆盖单元、集成、契约、回归以及适用的性能或安全验证？
- `H3`：验证项是否写明文件、涉及修改或复用的现有 case（或拟新增场景）、前置条件、命令或人工步骤、预期结果和通过标准？
- `H4`：验收步骤是否能证明需求达成且必须保持的旧行为未被破坏？
- `H5`：是否明确无法自动验证的部分、执行角色和留证方式？
- `H6`：是否区分实现、验证与独立最终核验，反向对照原始需求全集，并在实现或方案变化时使受影响证据失效？
- `H7`：新方案是否按风险完成必需的独立 Plan Review，核实发现并完成关键修订的受影响部分复审，且证据对应当前版本？用户明确批准降级时记录依据与限制；必需 Review 缺失且未获降级批准为阻塞。已有方案审查、影响分析及低风险可选 Review 按适用范围说明依据。

## I. 发布与回滚门禁

- `I1`：是否明确发布顺序、前置检查和责任边界？
- `I2`：是否定义成功指标、阈值、观测窗口、告警和响应责任？
- `I3`：是否定义回滚触发条件和可执行步骤？
- `I4`：数据、协议或配置变化能否安全回滚？不能时是否有前滚和恢复策略？
- `I5`：使用 `.ai` 开发资料时，是否保证最终 PR 新增提交不携带它，并在实际交付版本上重新测试和按明确范围 Review？

## J. 决策门禁

- `J1`：推荐方案是否说明取舍，而非只描述实现？
- `J2`：存在实质性替代路径时，备选方案是否真实可行且差异明确？
- `J3`：只有一条合理路径时，是否说明其他路径被排除的依据，而非虚构备选方案？
- `J4`：会改变方向、范围、风险或成本的方案选择，是否明确决策来源和批准门禁，并避免把未获批准的版本写成已确认或直接进入实施？
- `J5`：剩余风险、未知项和方案限制是否显式披露？

## 最终判定

新方案制定按`逐项预检 → 失败反演 → 修订方案 → 重新判定`执行。已有方案审查按`逐项预检原版本 → 失败反演 → 对同一原版本判定`执行；审查建议不能关闭原版本缺口，只有实际形成的新版本才能另走新方案门禁。每个 `quality_subject` 只在最后输出一次 `quality_status`：

- 任一项为`阻塞`：`阻塞`。
- 无阻塞项但存在`待处理`：仅当它们全部非关键且都有责任方或决策来源、处理时点和关闭条件时，判为`有条件通过`；否则判为`阻塞`。
- 所有适用项均为`已满足`，且失败反演未留下未处理的关键缺口：`通过`。

记录：`门禁 ID｜状态｜关键性｜证据或措施位置｜待办与关闭条件`，列出全部`待处理`和`阻塞`项。

不得使用数值评分覆盖上述规则。`quality_status` 只表示方案质量，不代表用户已批准；批准状态由独立的 `decision_status` 记录。
