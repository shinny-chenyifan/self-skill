# 完整方案流程

仅在主 Skill 判定需要完整方案制定或审查时读取。本文件的状态字段、编号和全量门禁不适用于轻量方案；workflow 内轻量方案的独立 Plan Review 规则见主 Skill。完整模式仍保留原有状态与交接契约。

## 状态模型

以下三类状态只描述方案，不表示实现或验收已完成。执行状态及证据按执行协议单独记录；普通检查点不升级 `plan_revision`。

分别记录以下状态，不得互相替代：

- `contract_status`：`就绪` / `待澄清`。只表示现有信息是否足以进入设计、审查或影响分析。
- `quality_status`：进入质量评估前为`未评估`；最终只能是`通过` / `有条件通过` / `阻塞`，只评价 `quality_subject` 指定方案版本的完整性、可实施性和可验证性，并按 [quality-gates.md](quality-gates.md) 判定。
- `decision_status`：`草案` / `待确认` / `已确认`。只表示方案的确切版本是否获得用户或有权限的决策来源批准。

按以下条件转换 `decision_status`：

- `草案`：任务契约待澄清，或方案内容仍在变化且尚未形成可供决策的确切版本。
- `待确认`：已形成并展示可识别的确切版本，但尚未获批准。
- `已确认`：用户或有权限的来源明确批准当前确切版本，并已记录 `confirmation_basis`。自动 workflow 只能在真实用户预授权覆盖当前任务、范围与交互模式，且主控已批准该确切版本时使用此状态；这不表示用户逐版确认。非自动 workflow 必须等待用户确认当前确切版本。

`quality_status` 不改变已有批准记录，`quality_status=通过` 也不代表 `decision_status=已确认`。方案的范围、架构、公共行为、数据、安全、兼容、验收或回滚发生实质变化后，尚未形成并展示确切新版本时保持`草案`；形成新版本后标记为`待确认`。

已有方案审查不得改写原方案的 `decision_status`；确认记录无法核实时，另记 `source_decision_status=未知`。能够核实时同时记录 `source_confirmation_basis`。提出实质修订时，为修订版本单独记录 `decision_status=待确认`。

## 工作流

### 1. 分流并形成任务契约

从用户请求、关联 plan 或 issue、项目文档和只读调研中形成任务契约：

- `task_type`
- 目标结果和用户价值
- 当前问题或现状
- `in_scope` 和 `out_of_scope`
- 必须保持不变的行为
- 行为、技术、兼容性、时间、成本或权限约束
- 带稳定编号、来源和确认状态的验收项，例如 `AC-1`
- 来源及可识别的版本
- `open_questions`
- `contract_status`

用户本轮明确请求可作为契约来源，不要为了形式重复确认。缺少信息时先判断能否通过只读调研发现，仅询问无法发现且会实质改变方案的问题。代码和现有文档可以证明当前状态，不能单独证明用户期望的目标行为。

解释冲突来源时，用户当前明确决策优先，其次是已确认的需求、plan 或 issue；代码、配置和测试只用于证明当前实现。来源版本不明、仍是草案或互相冲突时，将相关问题保留在 `open_questions`。

已有方案审查的任务契约描述“审查哪个版本、依据什么需求、审查哪些维度”，不要求被审方案本身已经完整。原方案中的歧义、缺失和冲突属于审查发现，不得因此把审查任务误标为 `contract_status=待澄清`。

仅在以下条件同时满足时标记 `contract_status=就绪`：

- 目标、包含范围、不包含范围和必须保持不变项已明确。
- 每个决定方向的 `AC-*` 都能追溯到用户或已确认来源；Agent 建议的验收项标记为`待确认提议`，不能自行把契约闭合。
- 多目标存在取舍时，优先级或允许牺牲的边界已确认。
- 没有会改变设计方向的来源冲突或关键未知项。

“优化”“提升可靠性”“减少耗时”“重构”等目标若缺少可观察成功标准、当前失败模式或目标间的取舍边界，默认属于关键未知项。可以先调研现状并给出选项，但不得据此冻结单一方案。

### 2. 调研当前实现

按任务需要检查：

- 项目指令、目录结构、相关文档和现有测试
- 入口、调用方、被调用方、数据流和状态变化
- 类型、协议、API、数据库、配置和依赖边界
- 相邻模块中的既有实现模式
- 构建、测试、部署、监控和回滚机制

记录关键证据的位置。不要为了显得全面而读取无关文件。

### 3. 建立事实与未知项清单

将调研结果分为：

- 已确认事实：有代码、配置、文档或运行结果支持
- 推断：由证据推导但尚未直接验证
- 假设：为继续设计暂时采用的前提
- 待确认问题：需要用户、业务方或外部系统确认

### 4. 执行澄清门禁

若 `open_questions` 中仍有会实质改变范围、架构、公共行为、数据、安全、兼容迁移、成本、核心验收、发布或回滚的问题：

- 将 `contract_status` 标记为 `待澄清`。
- 新方案制定时输出 `quality_status=未评估`、`decision_status=草案`；已有方案审查输出 `quality_status=未评估`，并保留原方案已有的确认记录；影响分析不输出 plan 状态。
- 只输出已知契约、证据、必要问题、推荐选项及选择影响，不进入详细设计或实施步骤。
- 不用未经确认的默认值、性能目标、超时、容量或范围补齐契约。

若信息完整且一致，或低风险未知项不会改变方向且已明确失效影响和关闭方式，将 `contract_status` 标记为 `就绪` 后继续。低风险假设不得伪装成已确认事实。

### 5. 设计、比较或审查

新方案制定先明确设计原则，再形成推荐方案。存在实质性替代路径时，比较：

- 正确性与需求覆盖
- 改动范围和复杂度
- 与现有架构的一致性
- 兼容性与迁移成本
- 风险、可测试性和可回滚性
- 性能、安全和运维成本

若只有一条合理路径，说明排除其他路径的原因，不要凑数。

已有方案审查以原方案为基线，逐项核对来源、事实、覆盖和门禁，区分阻塞缺口、非阻塞改进和已满足项。除非用户明确要求，不重写完整方案。影响分析只输出证据、影响边界、依赖、风险和未知项。

### 6. 编写可执行计划或审查结果

读取并使用 [plan-template.md](plan-template.md)。每个实施步骤至少说明：

- 修改目的及输入、输出、行为或结构的前后变化
- 文件路径及 class/function/test、配置键或文档章节等结构位置；新增项标记为拟新增，不虚构现有符号
- 前置依赖和顺序关系；跨 Agent 依赖写明提供方、产物、契约版本及解除阻塞条件，无依赖时写“无”
- 保持不变的约束及禁止修改的范围
- 完成后的验证方法及通过标准；修改或复用现有 case 时定位该 case，没有现成 case 时列出拟新增场景和预期结果
- 失败时的回退方式

避免使用“修改相关代码”“完善逻辑”等无法验证的表述。影响正确性或协作的事务边界、幂等策略、公共接口和错误语义等必须在方案中决定；局部变量、循环写法等留给实现者。行号可辅助定位，但不替代结构名称。

完整方案的每个 `STEP-*` 还必须形成可直接交给 Coder 的实施规格：写明被修改结构与相邻调用关系、输入/输出、正常与异常/边界行为、状态前后变化、允许的局部实现自由度，以及禁止由 Coder 决定的语义。不得把架构、公共接口、错误语义、兼容、事务、并发或范围选择留为“实现时决定”。所有 `STEP-*` 的计划前提必须可由仓库证据或已确认决策核验。

确切 `plan_revision` 只有在质量门禁、必要的独立 Plan Review 与有效确认均完成后，才是可派发的已批准实施规格；有效确认指非自动模式的用户确认，或自动 workflow 中真实用户预授权覆盖当前任务／范围／交互模式且主控批准该确切版本。Coder 在实现前逐项核验这些前提；发现不一致时停止受影响 `STEP-*`，报告差异证据、影响的 `AC/STEP/TEST` 与最小修订建议，返回本流程的调研和设计阶段。Coder 不得用局部代码变通、扩张范围或静默改写计划来消除差异。

多 Agent 执行时，由编排器将 `STEP-*` 映射为每个 Agent 的 Task Contract，保留位置、行为、依赖、约束和验收引用，不重新设计已确认的语义；独立代码 Review 仍在实现后执行。

同时列出本地 commit 计划：每个 commit 的精确范围、对应 `STEP-*`、依赖顺序、提交前验证和中文说明。不同 commit 无法可靠分离同一文件时，按提交顺序实施并提交，不在事后猜测拆分。

### 7. 执行完整性预检

新方案制定或已有方案审查必须完整读取 [quality-gates.md](quality-gates.md)，按其中的状态、证据和关键性规则逐项查找缺口。此时只记录问题，不产生最终 `quality_status`。

### 8. 进行失败反演

新方案制定或已有方案审查中，列出三至五个最可能导致方案失败的原因，并反查：

- 隐含调用方、数据消费者或范围遗漏
- 异常、边界、并发和部分失败
- 向后兼容、灰度迁移和存量数据
- 权限、安全、性能和资源上限
- 配置差异、可观测性、发布和回滚

### 9. 独立 Plan Review、修订与最终门禁

新方案在自检和失败反演后、最终输出给用户确认前，按风险执行独立 Plan Review：

- 单模块、局部、低风险且可逆：主 Agent 自检，独立 Review 可选。
- 跨模块、多 Agent 或公共接口：至少一个独立 Reviewer。
- 高风险（如安全权限、数据迁移或复杂并发）或复杂公共契约：两个独立 Reviewer，分别侧重需求与架构、正确性与验证；并发不足时顺序派发。

workflow 内的完整方案至少安排一个独立 Reviewer；高风险方案仍按上述覆盖执行。首次 Review 发现问题后，主 Agent 只修订一次并由独立 Reviewer 复审受影响部分；复审仍有阻断问题时停止交回外层主控，非阻断建议如实记录，不能因风格偏好无限循环。

Reviewer 的配置按 [agent-roster.md](agent-roster.md) 解析并提前展示。交接原始需求、补充决策、确切草案版本、仓库位置和相关证据入口；Reviewer 必须独立核对相关代码与测试，不只阅读主 Agent 的摘要。审查需求覆盖、事实准确性、结构定位、关键设计、任务边界与依赖以及验证有效性，并逐项判断实施规格是否足以让 Coder 仅执行而不重新设计。每条发现附证据位置、影响、关键性和最小修订建议；只读反馈，不代替主 Agent 修改方案或批准实施，不直接套用 PR Review 流程。

主 Agent 核实、去重并记录采纳或不采纳理由。关键缺口修订后由独立 Reviewer 复审受影响部分；若改变架构或公共契约，扩展到相关依赖和验收。记录审查版本、实际 Reviewer、完成状态、发现处置及复审证据，旧版本结论不能证明新版本已审查。无法完成必需 Review 时披露原因，质量门禁保持阻塞；只有用户明确选择降级，才能记录降级依据后按其余门禁评估，不宣称已完成独立 Review。

已有方案审查可由独立 Reviewer 承担，但仅对被审版本形成发现，不擅自修订；受派发的 Reviewer 不递归派发 Review。影响分析和契约待澄清的输出不启动本流程。

新方案制定先修订预检、失败反演和独立 Review 发现的缺口，完成必需复审，再将当前 `plan_revision` 作为 `quality_subject`，按 [quality-gates.md](quality-gates.md) 重新判定。

已有方案审查不得用审查者补充的证据或修订建议关闭原方案缺口；将被审的确切版本作为 `quality_subject`，按其现有内容判定。仅当用户明确要求并实际形成完整、可识别的新版本时，才能对新版本另行执行门禁。

最终 `quality_status` 只能在此步骤产生一次；不得在失败反演完成前宣称通过，也不得用数值评分替代门禁结论。已在步骤 4 被澄清门禁阻塞的任务直接结束，不执行此步骤。

### 10. 输出并请求用户确认

按照模板输出。新方案制定必须显式报告 `quality_subject`、`quality_status` 和 `decision_status`，不得用单一“方案状态”替代；已有方案审查报告被审版本对应的 `quality_subject`、`quality_status`、`source_decision_status`，没有形成完整修订版本时不得输出修订版本状态；影响分析报告 `contract_status` 和输出深度，不虚构 plan 状态。明确列出限制和需要用户确认的决策。自动 workflow 的批准必须记录真实预授权、主控批准的确切版本／范围和未越界、无关键质量阻塞的结论；非自动 workflow 必须等用户确认。当前方案版本未获有效确认或 `quality_status=阻塞` 时，不进入实施；已有批准不能覆盖质量阻塞。

完整模式的新方案制定必须在结论中逐项显示：

- `contract_status`
- `quality_subject=plan_revision`
- `quality_status`
- `decision_status`
- `plan_revision`
- `confirmation_basis`
