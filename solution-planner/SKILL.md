# 方案质量规划

## 目标

通过证据驱动的调研、任务契约、澄清门禁、影响分析和失败反演，稳定产出可执行的软件方案或可追溯的审查结论。保证流程和检查项被执行，不宣称能够发现未提供、不可访问或尚未确定的信息。

## 工作原则

- 先调研，后设计；不要仅凭需求描述猜测现状。
- 区分已确认事实、合理推断、工作假设和待确认问题。
- 关键未知项会改变范围、架构、公共契约、数据模型、安全、兼容迁移、验收或回滚时，暂停设计并向用户澄清。
- 优先最小改动和复用现有模式，避免无关重构。
- 只有存在实质性取舍时才列备选方案；给出推荐项、原因、代价和影响范围。
- 方案步骤必须指向可定位的模块、文件或接口，并附带对应验证方式。
- 用户只要求方案时保持只读；不要把制定方案扩展为实施、Git 操作或外部写入。
- 遵守仓库内 `AGENTS.md`、项目规范、权限和用户确认要求。

## 任务分流

先选择一个主任务类型：

- `新方案制定`：从需求和当前实现形成实施方案。
- `已有方案审查`：核对指定方案版本的证据、覆盖、风险和可执行性；默认输出问题与最小修订建议，不擅自重写整份方案。
- `影响分析`：只识别影响边界、依赖、风险和未知项；用户未要求实施方案时，不扩展为详细设计。

再选择输出深度：

- `精简模式`：仅用于单模块、局部、低风险且可逆的改动。
- `完整模式`：涉及跨模块依赖、公共接口、数据结构、状态或并发、权限安全、迁移、配置依赖、生产行为、显著性能影响或复杂回滚时使用；影响或风险不确定时也使用此模式。

新方案制定和已有方案审查在两种深度下都要筛查全部质量门禁。精简模式压缩输出，不代表删除检查项；影响分析按请求范围评估证据完整性，不生成 plan 门禁结论。

## 状态模型

分别记录以下状态，不得互相替代：

- `contract_status`：`就绪` / `待澄清`。只表示现有信息是否足以进入设计、审查或影响分析。
- `quality_status`：进入质量评估前为`未评估`；最终只能是`通过` / `有条件通过` / `阻塞`，只评价 `quality_subject` 指定方案版本的完整性、可实施性和可验证性，并按 [quality-gates.md](references/quality-gates.md) 判定。
- `decision_status`：`草案` / `待确认` / `已确认`。只表示方案的确切版本是否获得用户或有权限的决策来源批准。

按以下条件转换 `decision_status`：

- `草案`：任务契约待澄清，或方案内容仍在变化且尚未形成可供决策的确切版本。
- `待确认`：已形成并展示可识别的确切版本，但尚未获批准。
- `已确认`：用户或有权限的来源明确批准当前确切版本，并已记录 `confirmation_basis`。

`quality_status` 不改变已有批准记录，`quality_status=通过` 也不代表 `decision_status=已确认`。方案的范围、架构、公共行为、数据、安全、兼容、验收或回滚发生实质变化后，尚未形成并展示确切新版本时保持`草案`；形成新版本后标记为`待确认`。

已有方案审查不得改写原方案的 `decision_status`；确认记录无法核实时，另记 `source_decision_status=未知`。能够核实时同时记录 `source_confirmation_basis`。提出实质修订时，为修订版本单独记录 `decision_status=待确认`。

## 工作流

### 1. 分流并形成任务契约

从用户请求、关联 plan 或 issue、项目文档和只读调研中形成任务契约：

- `task_type`
- 目标结果和用户价值
- 当前问题或现状
- `in_scope` 和 `out_of_scope`
- 必须保持不变的行为
- 行为、技术、兼容性、时间、成本或权限约束
- 带稳定编号、来源和确认状态的验收项，例如 `AC-1`
- 来源及可识别的版本
- `open_questions`
- `contract_status`

用户本轮明确请求可作为契约来源，不要为了形式重复确认。缺少信息时先判断能否通过只读调研发现，仅询问无法发现且会实质改变方案的问题。代码和现有文档可以证明当前状态，不能单独证明用户期望的目标行为。

解释冲突来源时，用户当前明确决策优先，其次是已确认的需求、plan 或 issue；代码、配置和测试只用于证明当前实现。来源版本不明、仍是草案或互相冲突时，将相关问题保留在 `open_questions`。

已有方案审查的任务契约描述“审查哪个版本、依据什么需求、审查哪些维度”，不要求被审方案本身已经完整。原方案中的歧义、缺失和冲突属于审查发现，不得因此把审查任务误标为 `contract_status=待澄清`。

仅在以下条件同时满足时标记 `contract_status=就绪`：

- 目标、包含范围、不包含范围和必须保持不变项已明确。
- 每个决定方向的 `AC-*` 都能追溯到用户或已确认来源；Agent 建议的验收项标记为`待确认提议`，不能自行把契约闭合。
- 多目标存在取舍时，优先级或允许牺牲的边界已确认。
- 没有会改变设计方向的来源冲突或关键未知项。

“优化”“提升可靠性”“减少耗时”“重构”等目标若缺少可观察成功标准、当前失败模式或目标间的取舍边界，默认属于关键未知项。可以先调研现状并给出选项，但不得据此冻结单一方案。

### 2. 调研当前实现

按任务需要检查：

- 项目指令、目录结构、相关文档和现有测试
- 入口、调用方、被调用方、数据流和状态变化
- 类型、协议、API、数据库、配置和依赖边界
- 相邻模块中的既有实现模式
- 构建、测试、部署、监控和回滚机制

记录关键证据的位置。不要为了显得全面而读取无关文件。

### 3. 建立事实与未知项清单

将调研结果分为：

- 已确认事实：有代码、配置、文档或运行结果支持
- 推断：由证据推导但尚未直接验证
- 假设：为继续设计暂时采用的前提
- 待确认问题：需要用户、业务方或外部系统确认

### 4. 执行澄清门禁

若 `open_questions` 中仍有会实质改变范围、架构、公共行为、数据、安全、兼容迁移、成本、核心验收、发布或回滚的问题：

- 将 `contract_status` 标记为 `待澄清`。
- 新方案制定时输出 `quality_status=未评估`、`decision_status=草案`；已有方案审查输出 `quality_status=未评估`，并保留原方案已有的确认记录；影响分析不输出 plan 状态。
- 只输出已知契约、证据、必要问题、推荐选项及选择影响，不进入详细设计或实施步骤。
- 不用未经确认的默认值、性能目标、超时、容量或范围补齐契约。

若信息完整且一致，或低风险未知项不会改变方向且已明确失效影响和关闭方式，将 `contract_status` 标记为 `就绪` 后继续。低风险假设不得伪装成已确认事实。

### 5. 设计、比较或审查

新方案制定先明确设计原则，再形成推荐方案。存在实质性替代路径时，比较：

- 正确性与需求覆盖
- 改动范围和复杂度
- 与现有架构的一致性
- 兼容性与迁移成本
- 风险、可测试性和可回滚性
- 性能、安全和运维成本

若只有一条合理路径，说明排除其他路径的原因，不要凑数。

已有方案审查以原方案为基线，逐项核对来源、事实、覆盖和门禁，区分阻塞缺口、非阻塞改进和已满足项。除非用户明确要求，不重写完整方案。影响分析只输出证据、影响边界、依赖、风险和未知项。

### 6. 编写可执行计划或审查结果

读取并使用 [plan-template.md](references/plan-template.md)。每个实施步骤至少说明：

- 要改变的行为或结构
- 涉及的模块、文件、接口或数据
- 前置依赖和顺序关系
- 保持不变的约束
- 完成后的验证方法
- 失败时的回退方式

避免使用“修改相关代码”“完善逻辑”等无法验证的表述。

### 7. 执行完整性预检

新方案制定或已有方案审查必须完整读取 [quality-gates.md](references/quality-gates.md)，按其中的状态、证据和关键性规则逐项查找缺口。此时只记录问题，不产生最终 `quality_status`。

### 8. 进行失败反演

新方案制定或已有方案审查中，精简模式列出一至三个、完整模式列出三至五个最可能导致方案失败的原因，并反查：

- 隐含调用方、数据消费者或范围遗漏
- 异常、边界、并发和部分失败
- 向后兼容、灰度迁移和存量数据
- 权限、安全、性能和资源上限
- 配置差异、可观测性、发布和回滚

### 9. 修订并执行最终门禁

新方案制定先修订预检和失败反演发现的缺口，再将当前 `plan_revision` 作为 `quality_subject`，按 [quality-gates.md](references/quality-gates.md) 重新判定。

已有方案审查不得用审查者补充的证据或修订建议关闭原方案缺口；将被审的确切版本作为 `quality_subject`，按其现有内容判定。仅当用户明确要求并实际形成完整、可识别的新版本时，才能对新版本另行执行门禁。

最终 `quality_status` 只能在此步骤产生一次；不得在失败反演完成前宣称通过，也不得用数值评分替代门禁结论。已在步骤 4 被澄清门禁阻塞的任务直接结束，不执行此步骤。

### 10. 输出并请求评审

按照模板输出。新方案制定必须显式报告 `quality_subject`、`quality_status` 和 `decision_status`，不得用单一“方案状态”替代；已有方案审查报告被审版本对应的 `quality_subject`、`quality_status`、`source_decision_status`，没有形成完整修订版本时不得输出修订版本状态；影响分析报告 `contract_status` 和输出深度，不虚构 plan 状态。明确列出限制和需要用户确认的决策。当前方案版本未获明确确认或 `quality_status=阻塞` 时，不进入实施；已有批准不能覆盖质量阻塞。

新方案制定即使使用精简模式，也必须在结论中逐项显示：

- `contract_status`
- `quality_subject=plan_revision`
- `quality_status`
- `decision_status`
- `plan_revision`
- `confirmation_basis`

## 深度控制

- 小型、局部、低风险改动：使用精简模板，合并同类不适用项但保留边界依据。
- 高风险或跨边界改动：使用完整模板、稳定编号和端到端追踪矩阵。
- 影响分析使用相同的深度选择条件：精简模式输出直接影响与边界，完整模式额外追踪调用链、数据流、兼容迁移和运维影响。
- 无法访问代码或资料：输出“基于有限上下文的预案”，显式降低确定性并列出调研清单。

## 禁止事项

- 不把模板章节齐全等同于方案正确。
- 不隐藏未经验证的假设。
- 不虚构文件、接口、测试结果或现有行为。
- 不因用户要求“完整方案”而跳过关键澄清。
- 不把 `quality_status=通过` 写成用户已确认，也不继承未经核实的确认状态。
- 不在仅审查已有方案时擅自替换原方案。
- 不在缺少回滚或验证策略时把高风险方案标记为通过。
