# 分级方案规划与执行跟踪

## 目标与边界

按风险决定方案深度，按持续性决定是否跟踪执行，两者独立。日常实现与调试由当前开发 Agent 按项目规范完成；本 Skill 不要求所有开发任务先经过正式方案流程。

- 先只读调查事实，优先复用现有模式和最小改动。
- 区分已确认事实、推断、假设和待确认问题，不虚构文件、接口、确认或验证结果。
- 关键未知项影响范围、公共行为、数据、安全、兼容、验收或回滚时，先澄清，不用未经确认的默认值补齐设计。
- 用户只要求方案或分析时保持只读；执行须有明确授权。文件写入、Git 和外部操作继续遵守项目确认规则，方案质量通过不等于获得操作权限。
- 用户当前明确决策优先；代码和测试证明当前实现，不能单独证明用户期望。
- 诊断型任务的 problem framing 至少区分期望、实际、复现条件和验收标准；根因结论必须与证据、推断和未知项分开。非诊断的 feature 任务不强加根因要求。

## 入口选择

先判断用户要制定方案、审查已有方案、影响分析，还是执行已确认方案。再按以下入口处理，不把执行恢复重新展开为方案制定：

| 入口 | 适用条件 | 读取内容 |
| --- | --- | --- |
| 轻量方案 | 用户明确要求制定或审查方案，且目标明确、范围局部、低风险、可逆并易于验证 | 本文件即可；需要模板时只读 plan-template.md 的轻量部分 |
| 完整方案 | 跨模块行为或契约变化、公共接口兼容性、交易与资金逻辑、数据迁移、复杂状态或并发、权限安全、重大性能影响、复杂回滚，或正式并行编排需要完整交接 | 完整读取 [full-plan.md](references/full-plan.md)，按流程读取模板与门禁 |
| 执行跟踪／恢复 | 已授权实施，且有多个里程碑、大量独立事项、跨会话或明显上下文增长 | 读取 [execution-protocol.md](references/execution-protocol.md)，复用已确认方案与唯一状态来源 |

目标明确的局部低风险小改动，且用户未要求方案时，无需调用本 Skill；简述目标、范围、步骤和验证，并遵守写入确认即可。文件数和预计耗时只作辅助信号：单文件下单逻辑也可能高风险，多文件文案替换不因此进入完整模式。

风险不明时先只读调查；关键未知项向用户澄清，不能直接假定低风险。普通长任务不因耗时长自动启用完整方案；完整方案的短任务也不因此必须创建执行账本。执行中发现风险升级时暂停受影响修改，补充完整方案及确认后再继续。

仅请求影响分析时输出事实证据、影响边界、依赖、风险和未知项，深度与影响相匹配；不扩展为实施计划，不输出方案质量状态或启动 Plan Review。

## 轻量方案

用简洁自然语言交付以下四项，不强制固定表格或字段名：

1. 目标：用户希望改变什么，当前问题的相关证据是什么。
2. 范围：拟修改的文件及结构位置、行为变化和必须保持的约束。
3. 步骤：最小实施顺序；写明具体修改逻辑、相关调用关系、输入输出、必要字段或变量、正常／失败／边界行为、事实前提、禁止范围、验证和恢复方式。文档任务以章节、规则和前后语义代替代码函数。只有存在实质取舍时比较选项并说明推荐理由。
4. 验证：可执行的检查或人工操作、预期结果；区分计划验证与实际执行结果。每个 commit 写明范围、对应步骤、依赖顺序、提交前验证和中文说明；小任务可以只有一个 commit。

存在实际风险、未决问题或恢复注意事项时补充说明，不为凑模板编造风险。输出明确方案是否待确认；已有明确授权时引用其依据，不重复索要相同授权。

独立使用本 Skill 的轻量方案不强制三轴状态、plan_revision、AC/STEP/TEST 编号、失败反演、A–J 全量门禁、独立 Plan Review、Agent 清单或持久 JSON。主 Agent 对需求覆盖、影响范围和验证有效性自检即可，不能把省略正式门禁写成“完整门禁已通过”。

workflow 内的轻量方案仍使用精简格式，但必须具备上述可直接实施的语义、可定位的确切版本和 commit 计划；简略模式由当前主 Agent 整理输入并制定方案，不另建 Planner 或 plan session。workflow 必须安排独立 Plan Review：多 session 由 plan session 协调，简略模式由当前主 Agent 派发 Plan Reviewer 子 Agent。首次发现问题后只修订一次并复审受影响部分；复审仍有阻断问题时交回主控，非阻断建议如实记录，不因风格偏好无限循环。该轮次规则不降低高风险方案所需的审查覆盖。

轻量方案不强制粘贴完整代码；Coder 只可决定不改变已批准语义的局部命名、私有函数拆分和等价写法，不能把影响行为的设计留到编码时决定。

自动模式只有在无关键质量阻塞、未越出用户需求与真实预授权边界时，才由主控批准确切版本并保留预授权来源；不得把它写成用户逐版确认。非自动模式将合格方案交回主控请求用户确认，简略模式由当前主 Agent 直接展示并请求确认。实质修改形成新版本并重新检查受影响部分；自动模式仍受原预授权边界限制，非自动模式重新确认。

执行或 Review 的新证据否定需求／problem framing、诊断根因或关键 Plan 前提时，先重建受影响层，再形成新的 `plan_revision`、完成必要 Plan Review 和有效确认。历史 `decision_status` 不改写，只记录其对当前版本的适用性失效；轻量方案只记录必要的前提与失效影响，不强制完整 schema。

轻量审查说明被审材料、依据、问题及证据、影响和最小修订建议，不擅自重写原方案或改写其确认状态。被审方案原有正式状态按原文保留为来源，不用轻量审查结果替代其正式门禁结论；发现高风险缺口时升级完整审查。

## 完整方案与正式交接

完整模式保留三轴状态、需求与验收追踪、失败反演、按风险的独立 Plan Review、版本确认、验证与回滚。详细规定集中在 [full-plan.md](references/full-plan.md)、[plan-template.md](references/plan-template.md) 和 [quality-gates.md](references/quality-gates.md)，仅按完整流程读取。

完整方案在 `quality_status=通过|有条件通过` 且 `decision_status=已确认` 后，才可作为 **已批准实施规格（Approved Implementation Plan）** 交给 Coder。它不是高层建议，而是 Coder 的主要输入；必须逐个 `STEP-*` 提供可核验的文件、结构位置、调用关系、输入/输出、前后行为、错误与边界语义、状态变化、禁止范围、验证和回退。缺少会改变语义的细节时，不得把选择留给 Coder，必须在规划或 Plan Review 阶段补齐。

Coder 只可在不改变已批准语义的前提下决定局部实现写法，例如变量命名、私有函数拆分和等价控制流。Coder 不得重设计架构、改变公共接口或错误语义、扩大范围、补造需求，或因实现不便静默改计划。实现前必须核验计划所依赖的代码事实、接口和测试入口；发现任一前提不成立，立即停止受影响步骤，报告差异、证据、影响的 `STEP/AC/TEST` 和最小修订建议，返回规划阶段。未经修订、重新审查并确认的 `plan_revision` 不得继续受影响实现。

`parallel-feature-workflow` 的原独立完整流程消费完整 Planning Handoff；轻量方案接入该原流程前，必须补齐完整契约、质量评估和确切版本确认，不能仅添加“通过”状态后交接。低风险、代码级轻量方案可进入 `workflow-code-session`，但高风险任务仍使用完整规划。方案版本及确认由本 Skill 负责，编排运行态由编排器独占，不维护第二份进度。

`execution-protocol.md` 中既有 parallel 账本只适用于上述原独立完整流程。进入 `workflow-code-session` 后，全局阶段、运行记录与决策由外层 workflow 主控独占；本 Skill 只保留方案版本、审查与确认依据以及初始分工／运行态定位，不创建或更新第二份全局账本。

`local-pr-review` 负责正式、多视角、固定范围的独立代码审查。普通小改不自动启动五视角 Review；正式并行流程仍遵守其既有 Review 契约、证据与阻塞规则。

## Agent 配置

实际需要派发、新增 Agent 或改变配置时读取 [agent-roster.md](references/agent-roster.md)，展示有效配置、来源及用户可修改方式；相同配置已展示时不因方案输出或阶段切换重复播报。单 Agent 日常任务不强制配置清单。

配置按“用户对具体 Agent、角色或任务的当前指令 > workflow 主控的显式配置 > 既有默认或 `strict-plan-execution` 预设 > 继承当前”解析；用户固定角色偏好通过既有 agent_policy 指定。每个显式组合均按当前派发工具能力核验，不静默替换，不将建议配置写成实际执行证据。

## 快速处理与降级

独立使用本 Skill 且用户要求快速实现时，低风险任务可采用轻量流程，省略正式模板和额外审查。workflow 内的轻量方案仍必须执行独立 Plan Review。高风险任务若拟省略必需检查，先明确具体检查、理由、影响与剩余风险，取得明确降级决策并记录；“快点做”本身不是降级授权。

降级不得把未解决的关键未知项、失败或未执行的必要验证、范围冲突、权限限制记为通过。不得绕过已有文件写入或 Git 确认要求；无法证明完成时如实报告缺口。用户批准降级不等于完整门禁已经通过。
